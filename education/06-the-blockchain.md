# The Blockchain

At the heart of Bitcoin Cash is a data structure called the **blockchain** — an ordered, back-linked list of blocks of transactions. It's the public ledger that records every payment ever made, and it's what makes Bitcoin Cash a *trustless* system: instead of trusting a bank or a server to keep the books, every participant can independently verify the entire history of the network.

In this lesson we'll open up that data structure and look at how blocks are built, how they're chained together, and how a clever tree of hashes lets lightweight wallets verify payments without downloading the whole chain.

## A chain of blocks

The blockchain is a **sequential ledger** where each block points to its predecessor. Blocks are linked "back" — each one contains a reference to the block that came before it — creating a chain that runs all the way back to the very first block, the *genesis block*.

The blockchain can be stored as a flat file or in a simple database. The **Bitcoin Cash Node (BCHN)** reference client stores the blockchain metadata using Google's **LevelDB**, a fast key-value database.

The blockchain is often visualized as a vertical stack, with blocks layered on top of each other and the first block as the foundation. That image gives us the vocabulary: **height** is the distance from the first block, and the **top** or **tip** is the most recently added block.

Each block is identified by a **hash** — a digital fingerprint generated by running the block header through the SHA-256 algorithm. Each block also references its *parent* block through a "previous block hash" field in its header. In other words, every block contains the hash of its parent inside its own header. The sequence of hashes linking each block to its parent creates a chain back to the genesis block.

### Forks and immutability

Although a block has just one parent, it can temporarily have multiple *children*. This happens during a **fork**, when different miners discover blocks almost simultaneously. Each child refers to the same parent block. Eventually the network converges on a single canonical chain and the fork is resolved — only one child becomes part of the blockchain.

The "previous block hash" field lives inside the block header, so it affects the *current* block's hash. If a parent block is modified in any way, its hash changes — which forces a change in the child's "previous block hash" pointer, which changes the child's hash, which forces a change in the grandchild, and so on. This **cascade effect** means that once a block has many generations built on top of it, it cannot be changed without recalculating all subsequent blocks. Because that recalculation would require enormous computation, a long chain of blocks makes the blockchain's deep history effectively **immutable** — a key feature of Bitcoin Cash's security.

One way to think about it is like layers in a geological formation. The surface layers might shift with the seasons, but a few inches down the layers become more stable, and hundreds of feet down you're looking at a snapshot of the past that has remained undisturbed for millions of years. In the blockchain, the most recent few blocks might be revised during a fork — the top six blocks are like a few inches of topsoil. But go deeper and blocks become less and less likely to change. After 100 blocks, the **coinbase transaction** (the one containing newly mined coins) can be spent. A few thousand blocks back — about a month — and the blockchain is settled history for all practical purposes. The protocol always allows a chain to be undone by a longer chain, so the possibility of reversal always exists, but the probability decreases with time until it becomes infinitesimal.

## Structure of a block

A block is a **container data structure** that aggregates transactions for inclusion in the public ledger. It's made of a **header**, containing metadata, followed by a long list of transactions that make up the bulk of its size.

The block header is just **80 bytes**, while the average transaction is at least 250 bytes. A complete 32 MB Bitcoin Cash block can hold nearly 128,000 transactions — making a full block roughly 400,000 times larger than its header.

| Size               | Field               | Description                                                  |
| :----------------- | :------------------ | :----------------------------------------------------------- |
| 4 bytes            | Block Size          | The size of the block, in bytes, following this field        |
| 80 bytes           | Block Header        | Several fields form the block header                         |
| 1–9 bytes (VarInt) | Transaction Counter | How many transactions follow                                 |
| Variable           | Transactions        | The transactions recorded in this block                      |

Every block contains exactly one **coinbase transaction** — created by the miner — followed by zero or more standard transactions. The coinbase input doesn't consume existing satoshis; instead it creates new value from the **block reward** (which starts at 50 BCH and halves every 210,000 blocks) plus the **transaction fees** from the block's other transactions.

## The block header

The block header is a fixed-width, 80-byte summary of a block. Because it's so small, nodes can perform critical validity checks before committing to the expensive process of downloading and validating every transaction in the block. The header lets a node:

1. **Calculate the block hash** — the block's identity is the double-SHA-256 hash of its header.
2. **Verify proof-of-work** — confirm the block hash is below the required target.
3. **Establish its position** — use the "previous block hash" to place the block in the chain.

The header consists of three sets of metadata: a reference to the previous block, the mining-related fields (*difficulty target*, *timestamp*, *nonce*), and the **merkle root** — a data structure that efficiently summarizes all the transactions in the block.

| Size     | Field               | Description                                                           |
| :------- | :------------------ | :-------------------------------------------------------------------- |
| 4 bytes  | Version             | The block format version (currently `0x04000000`)                      |
| 32 bytes | Previous Block Hash | A reference to the hash of the previous (parent) block in the chain   |
| 32 bytes | Merkle Root         | A hash of the root of the merkle tree of this block's transactions    |
| 4 bytes  | Timestamp           | The approximate creation time of this block (seconds from Unix Epoch) |
| 4 bytes  | Target              | The compressed target the block hash must be below to be valid        |
| 4 bytes  | Nonce               | A counter used for the proof-of-work algorithm                        |

The **nonce**, **target**, and **timestamp** are the fields used in the mining process. The target uses a compact floating-point representation to keep the header small: the value is calculated as *significand × 2^(8 × (exponent − 3))*.

## Block identifiers: block hash and block height

The primary identifier of a block is its **cryptographic hash** — a digital fingerprint made by hashing the block header twice through the SHA-256 algorithm. The resulting 32-byte hash is called the *block hash* (more accurately the *block header hash*, since only the header is used to compute it). For example, `000000000019d6689c085ae165831e934ff763ae46a2a6c172b3f1b60a8ce26f` is the block hash of the first Bitcoin Cash block ever created.

The block hash identifies a block uniquely and unambiguously, and any node can independently derive it by simply hashing the block header. Note that the block hash is *not* actually stored inside the block's data structure — neither when transmitted on the network nor when stored on disk. Instead, each node computes it as the block is received. The hash may be stored in a separate database table as metadata to speed up indexing and retrieval.

A second way to identify a block is by its **position** in the blockchain, called the **block height**. The first block ever created is at height 0. Each subsequent block added "on top" is one position higher, like boxes stacked on top of each other. As of August 2026, the Bitcoin Cash blockchain is roughly **963,000 blocks** tall.

Unlike the block hash, the block height is **not** a unique identifier. A single block always has a specific, invariant height, but the reverse isn't true — two or more blocks can compete for the same height during a fork. The height is also not part of the block's data structure; each node dynamically determines a block's position when it receives it.

> A block's *block hash* always identifies a single block uniquely. A block also always has a specific *block height*. But a specific block height does not always identify a single block — two or more blocks might compete for the same position in the chain.

## The genesis block

The first block in the blockchain is called the **genesis block**, created in 2009. It's the common ancestor of all blocks — if you start at any block and follow the chain backward, you'll eventually arrive at the genesis block.

Every node always starts with a blockchain of at least one block, because the genesis block is **statically encoded** in the Bitcoin Cash client software and cannot be altered. Every node "knows" the genesis block's hash, structure, creation time, and even the single transaction within it. This gives every node a secure, trusted "root" from which to build the blockchain.

The genesis block's hash is:

```
000000000019d6689c085ae165831e934ff763ae46a2a6c172b3f1b60a8ce26f
```

You can look it up in any block explorer, such as [Explorer by Bitcoin.com](https://explorer.bitcoin.com/bch/block/000000000019d6689c085ae165831e934ff763ae46a2a6c172b3f1b60a8ce26f) or [Blockchair](https://blockchair.com/bitcoin-cash/blocks).

The genesis block contains a hidden message. Its coinbase transaction input contains the text *"The Times 03/Jan/2009 Chancellor on brink of second bailout for banks."* This was intended as proof of the earliest date the block was created, by referencing the headline of the British newspaper *The Times*. It also serves as a tongue-in-cheek reminder of the importance of an independent monetary system — Bitcoin Cash's launch coincided with an unprecedented worldwide monetary crisis. The message was embedded in the first block by Satoshi Nakamoto.

### Inspecting the genesis block with bch-js

The modern way to query block data from JavaScript is the **bch-js** library (the actively-maintained successor to the deprecated BITBOX). Here's how to fetch the genesis block's details:

```javascript
const BCHJS = require("@psf/bch-js");
const bchjs = new BCHJS();

async function getGenesisBlock() {
  try {
    const block = await bchjs.Blockchain.getBlock(
      "000000000019d6689c085ae165831e934ff763ae46a2a6c172b3f1b60a8ce26f"
    );
    console.log(block);
  } catch (err) {
    console.error(err);
  }
}

getGenesisBlock();
```

The result includes the block's hash, height, merkle root, timestamp, nonce, difficulty, and the list of transactions it contains.

You can also query the current state of the chain with `bchjs.Blockchain.getBlockCount()` (the latest block height) and `bchjs.Blockchain.getBlockHash(height)` (the hash of the block at a given height).

## Linking blocks in the blockchain

Bitcoin Cash full nodes maintain a local copy of the blockchain, starting at the genesis block, and constantly update it as new blocks are found. When a node receives an incoming block, it validates it and then links it to the existing chain by examining the "previous block hash" in the incoming block's header.

Suppose a node has 277,314 blocks in its local copy, and the last block it knows about has the header hash `00000000000000027e7ba6fe7bad39faf3b5a83daed765f05f7d1b71a1632249`. The node then receives a new block from the network:

```javascript
{
  "size" : 43560,
  "version" : 2,
  "previousblockhash" :
  "00000000000000027e7ba6fe7bad39faf3b5a83daed765f05f7d1b71a1632249",
  "merkleroot" :
  "5e049f4030e0ab2debb92378f53c0a6e09548aea083f3ab25e1d94ea1155e29d",
  "time" : 1388185038,
  "difficulty" : 1180923195.25802612,
  "nonce" : 4215469401,
  "tx" : [
    "257e7497fb8bc68421eb2c7b699dbab234831600e7352f0d9e6522c7cf3f6c77",
    // ... many more transactions omitted ...
    "05cfd38f6ae6aa83674cc99e4d75a1458c165b7ab84725eda41d018a09176634"
  ]
}
```

Looking at the `previousblockhash` field, the node finds a hash it already knows — that of the last block on its chain at height 277,314. So this new block is a *child* of that block and extends the chain. The node adds it to the end, making the blockchain one block longer at height 277,315.

## Merkle trees

Each block contains a summary of all its transactions using a **merkle tree** — also known as a *binary hash tree*. This is a data structure used to efficiently summarize and verify the integrity of large sets of data. Merkle trees are binary trees containing cryptographic hashes. (In computer science, "tree" describes a branching data structure, but these trees are usually drawn upside down, with the "root" at the top and the "leaves" at the bottom.)

A merkle tree is constructed **bottom-up** by recursively hashing pairs of nodes until only one hash remains — the **root**, or **merkle root**. The hash algorithm used is **double-SHA256** (SHA-256 applied twice). The resulting 32-byte merkle root is stored in the block header, summarizing all the data in all the block's transactions.

In the example below, we start with four transactions, A, B, C, and D, which form the *leaves* of the tree. The transactions aren't stored in the tree; instead their data is hashed, and the resulting hash is stored in each leaf node as H~A~, H~B~, H~C~, and H~D~:

```
H~A~ = SHA256(SHA256(Transaction A))
```

Consecutive pairs of leaf nodes are then summarized in a parent node by concatenating the two hashes and hashing them together. To construct the parent node H~AB~, the two 32-byte child hashes are concatenated into a 64-byte string, which is then double-hashed:

```
H~AB~ = SHA256(SHA256(H~A~ + H~B~))
```

The process continues until there's a single node at the top — the merkle root.

![Calculating the nodes in a merkle tree](/block-blog/images/mastering-bitcoin-cash/msbt_0702.png)

Because a merkle tree is a binary tree, it needs an even number of leaf nodes. If there's an odd number of transactions, the last transaction hash is duplicated to create an even number of leaves — a *balanced tree*. In the diagram below, transaction C is duplicated.

![Duplicating one data element achieves an even number of data elements](/block-blog/images/mastering-bitcoin-cash/msbt_0703.png)

The same method generalizes to trees of any size. Bitcoin Cash blocks commonly contain several hundred to more than a thousand transactions, all summarized into a single 32-byte merkle root. Whether there's one transaction or a hundred thousand, the merkle root always summarizes them into 32 bytes.

![A merkle tree summarizing many data elements](/block-blog/images/mastering-bitcoin-cash/msbt_0704.png)

### Why merkle trees matter

Merkle trees give Bitcoin Cash two big advantages:

- **Efficient updates.** When mining a block, new transactions can be added without re-hashing the entire dataset — only the small number of hashes on the path to the root need to be recalculated.
- **Efficient verification.** To prove a specific transaction is included in a block, a node only needs to produce a **merkle path** (or *authentication path*) — the minimal set of hashes connecting that transaction to the root. With N transactions, verifying inclusion takes at most 2·log₂(N) calculations.

To prove that transaction K is included in a block, a node produces a merkle path of just four 32-byte hashes (shown in blue below): H~L~, H~IJ~, H~MNOP~, and H~ABCDEFGH~. With those four hashes, any node can prove that H~K~ (in green) is part of the merkle root by computing four additional pair-wise hashes.

![A merkle path used to prove inclusion of a data element](/block-blog/images/mastering-bitcoin-cash/msbt_0705.png)

The efficiency becomes obvious as scale increases:

| Number of Transactions | Approx. size of block | Path size (hashes) | Path size (bytes) |
| :--------------------- | :-------------------- | :----------------- | :---------------- |
| 16 Tx                  | 4 Kilobytes           | 4 hashes           | 128 bytes         |
| 512 Tx                 | 128 Kilobytes         | 9 hashes           | 288 bytes         |
| 2048 Tx                | 512 Kilobytes         | 11 hashes          | 352 bytes         |
| 65,535 Tx              | 16 megabytes          | 16 hashes          | 512 bytes         |

While the block size grows rapidly — from 4 KB with 16 transactions to 16 MB with 65,535 — the merkle path needed to prove a transaction's inclusion grows much more slowly, from 128 bytes to just 512 bytes.

### Seeing a merkle root with bch-js

We can use **bch-js** to fetch the latest block and inspect its merkle root:

```javascript
const BCHJS = require("@psf/bch-js");
const bchjs = new BCHJS();

async function showMerkleRoot() {
  try {
    // Get the latest block
    const height = await bchjs.Blockchain.getBlockCount();
    const blockHash = await bchjs.Blockchain.getBlockHash(height);
    const block = await bchjs.Blockchain.getBlock(blockHash);

    console.log(`Block height: ${height}`);
    console.log(`Merkle root: ${block.merkleroot}`);
    console.log(`Transactions in block: ${block.tx.length}`);
  } catch (err) {
    console.error(err);
  }
}

showMerkleRoot();
```

## Merkle trees and simplified payment verification (SPV)

Merkle trees are used extensively by **simplified payment verification (SPV)** nodes — lightweight clients that don't store the full blockchain. SPV nodes download only the **block headers** (80 bytes each), not the transactions inside each block. The resulting header chain is roughly 1,000 times smaller than the full blockchain.

To verify that a transaction is included in a block, an SPV node:

1. Asks a peer for a **merkle path** — a compact cryptographic proof linking the transaction to the block header.
2. Verifies the transaction's hash against the **merkle root** stored in that header.
3. Verifies the header chain itself by checking proof-of-work.

Consider an SPV node interested in incoming payments to an address in its wallet. It establishes a **bloom filter** on its connections to peers to limit the transactions it receives to only those containing addresses of interest. When a peer sees a matching transaction, it sends the block using a **`merkleblock`** message, which contains the block header plus a merkle path linking the transaction of interest to the merkle root. The SPV node uses this path to connect the transaction to the block, and the block header to link the block to the rest of the chain. Together, these two links prove the transaction is recorded in the blockchain.

All in all, the SPV node receives less than a kilobyte of data for the header and merkle path — more than a thousand times less than a full block. This is what makes lightweight mobile wallets practical.

## Wrap up

Let's summarize what we've covered:

1. **A chain of blocks** — the blockchain is an ordered, back-linked list where each block's header contains the hash of its parent, running back to the genesis block.
2. **Immutability** — the cascade of hashes means deep history can't be changed without re-mining all subsequent blocks.
3. **Block structure** — a block is an 80-byte header plus a list of transactions, capped at 32 MB.
4. **The block header** — version, previous block hash, merkle root, timestamp, target, and nonce.
5. **Block identifiers** — a block is uniquely identified by its hash, and also has a (non-unique) height.
6. **The genesis block** — the statically-encoded first block, containing Satoshi's hidden message.
7. **Merkle trees** — a binary hash tree that summarizes all a block's transactions into a single 32-byte root.
8. **SPV** — lightweight nodes use merkle paths to verify transactions without downloading the full chain.

The blockchain is the trustless foundation of Bitcoin Cash — a public, immutable ledger that anyone can verify. In the next lesson we'll look at how new blocks are actually created: the mining process and consensus.
